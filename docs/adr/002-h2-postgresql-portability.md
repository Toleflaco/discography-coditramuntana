# ADR-002: Portabilidad de base de datos — H2 file mode en desarrollo, portable a PostgreSQL

Status: Accepted
Date: 2026-08-27

## Contexto

El PDF del enunciado indica explícitamente: *"Use sqlite3 as the database
adapter"*. Es una instrucción imperativa, no una sugerencia. El correo
posterior del equipo de People & Talent autoriza libertad tecnológica
("puedes utilizar el lenguaje o tecnologías con las que te sientas más
cómodo") pero no menciona la BD explícitamente. Se aplica la interpretación
de que la libertad tecnológica del correo cubre también la elección de BD.

Tres fuerzas condicionan la decisión:

1. **Instrucción del PDF sobre BD:** *"Use sqlite3 as the database adapter"*.
2. **Libertad tecnológica autorizada por correo:** aplicada por transitividad
   a la elección de BD.
3. **Requisito operativo:** la BD debe poder arrancar en la máquina del
   revisor sin instalación previa ni configuración externa, para que la
   evaluación del proyecto no dependa del entorno.

## Alternativas consideradas

### SQLite (lo que pide el PDF)

SQLite es lo que pide el PDF, pero presenta dos problemas técnicos en un
proyecto Java + Spring Data JPA. Primero, el driver JDBC existe pero
Hibernate no incluye un dialect oficial para SQLite; los dialects
disponibles son librerías de terceros no mantenidas por el equipo core de
Hibernate, con riesgo real de incompatibilidades al actualizar Spring Boot
o Hibernate. Segundo, el sistema de tipos de SQLite es laxo (type affinity
con conversiones implícitas) y choca con la filosofía de tipos estrictos
que asumen JPA y Bean Validation.

### PostgreSQL

PostgreSQL es la BD "de producción" natural en el ecosistema Spring/Java:
dialect oficial en Hibernate, tipos estrictos, ecosistema maduro.
Descartada como BD de desarrollo por el requisito operativo del Context:
el revisor tendría que instalar el servidor PostgreSQL, arrancar el
servicio, crear usuario y BD, configurar credenciales. Cada paso es
fricción y potencial punto de fallo en la evaluación del proyecto. La
alternativa moderna para evitar esa fricción sería Docker + Testcontainers,
pero implica añadir Docker como dependencia adicional del entorno de
desarrollo y ampliar el scope técnico de la prueba en varias horas, sin
aportar al eje declarado por el cliente (backend sólido y bien
desarrollado). La decisión no cierra la puerta a PostgreSQL: el código se
escribe de forma portable (ver Decisión), lo que preserva la opción de
migrar cuando el proyecto salga del ámbito de prueba técnica.

### H2 (elegida)

H2 en file mode combina las ventajas de las otras dos alternativas sin sus
inconvenientes principales. Frente a SQLite: dialect oficial en Hibernate
(`H2Dialect` en el core, sin dependencia de terceros), sistema de tipos SQL
estándar compatible con la filosofía JPA, y consola web integrada
(`/h2-console`) para inspección empírica de la BD durante desarrollo sin
herramientas externas. Frente a PostgreSQL: cero instalación en la máquina
del revisor, la aplicación arranca directamente contra un fichero local
(`data/discography.mv.db`) que se crea automáticamente en el primer arranque.

## Decisión

El proyecto usa **H2 Database en file mode** como BD de desarrollo
(`data/discography.mv.db`), con las siguientes decisiones técnicas que
preservan portabilidad hacia PostgreSQL sin modificar código de negocio ni
entidades:

- **`@Lob` en campos de texto largo** (`Artist.description`,
  `Lp.description`). Anotación JPA estándar; el driver JDBC de cada motor
  decide el tipo concreto (`CLOB` en H2 y Oracle, `TEXT` en PostgreSQL).
  Se evita explícitamente `columnDefinition = "TEXT"` u otras variantes
  que acoplarían el código a un motor específico.

- **`@Size(max=5000)` en los DTOs de entrada** (`ArtistCreateRequest`,
  `ArtistUpdateRequest`, `LpCreateRequest`, `LpUpdateRequest`) para el
  campo `description`. Límite razonable para descripciones textuales en
  el dominio. Compatible con `@Lob` en ambos motores (H2 `CLOB` y
  PostgreSQL `TEXT` aceptan tamaños muy superiores).

- **Migraciones Flyway con SQL estándar** (`V1__create_schema.sql`). Uso
  de `BIGINT GENERATED BY DEFAULT AS IDENTITY`, sintaxis SQL:2003 portable
  entre H2, PostgreSQL 10+, Oracle 12c+ y DB2. Se descarta explícitamente
  `AUTO_INCREMENT` (específico de MySQL) y `SERIAL` (específico de
  PostgreSQL en versiones legacy), que romperían la portabilidad. Uso de
  `VARCHAR(n)` y `CLOB` estándar. Constraints `FOREIGN KEY`, `UNIQUE` y
  `PRIMARY KEY` en sintaxis estándar. Ninguna sentencia depende de
  dialecto específico.

- **`spring.jpa.hibernate.ddl-auto: validate`**. Hibernate no crea ni
  modifica el schema; solo verifica que las entidades cuadran con el
  schema existente al arrancar. Flyway es la única fuente de verdad del
  schema. Esto garantiza que el schema es idéntico en cualquier motor
  porque no depende de la generación automática de Hibernate (que
  introduce diferencias entre dialects).

- **Sin configuración explícita de `hibernate.dialect`**. Hibernate
  auto-detecta el dialect a partir del driver JDBC y de la URL de
  conexión (`jdbc:h2:...` → `H2Dialect`; `jdbc:postgresql://...` →
  `PostgreSQLDialect`). Al migrar a PostgreSQL, basta con cambiar URL y
  driver; el dialect se resuelve solo.

- **Tipos JPA estándar en las entidades** (`Long`, `String`, colecciones
  estándar). Ninguna anotación específica de motor.

## Consecuencias

### Positivas

- **Portabilidad demostrada por construcción, no por promesa.** Cada
  elemento del código (`@Lob`, migraciones Flyway estándar,
  `ddl-auto: validate`, ausencia de dialect explícito) es verificable. Un
  revisor puede abrir cualquiera de esos ficheros y comprobar la
  afirmación. La portabilidad no es una promesa a futuro — es una propiedad
  presente del código.

- **Onboarding del revisor sin fricción.** Consecuencia operativa: clonar
  repo + `./mvnw spring-boot:run` + navegador a `localhost:8080`. Sin
  instalación de BD, sin credenciales, sin Docker. La aplicación arranca
  contra un fichero local que se crea automáticamente en el primer
  arranque, con el schema aplicado por Flyway y los datos aplicados por
  el DataSeeder.

- **Inspección empírica durante desarrollo.** H2 Console (`/h2-console`)
  permite verificar el estado real de la BD sin herramientas externas.
  Consecuencia directa: la verificación empírica (regla operativa del
  proyecto) es posible sin dependencias adicionales.

### Negativas

- **H2 no es una BD de producción.** Su uso está limitado a desarrollo y
  tests. Antes de un despliegue productivo real, la migración a PostgreSQL
  (o motor equivalente) es requisito, no opción. Este ADR documenta cómo
  esa migración es trivial gracias a las decisiones de portabilidad, pero
  no la ha ejecutado.
